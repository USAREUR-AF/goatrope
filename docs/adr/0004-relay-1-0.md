# ADR 0004: The relay reaches 1.0: a service, TCP, multicast, address proxy, remote mirror and an opt-in layer-2 lane

| Field | Value |
|---|---|
| Status | Accepted |
| Date | 2026-11-27 |
| Deciders | operator |
| Owner | `goat-owners` |
| Related | [ADR 0002](0002-relay.md) (amended here), [ADR 0003](0003-goatrope-is-written-in-rust.md) |

## Decision

goatrope over a WireGuard mesh does everything a layer-2 overlay network such as
ZeroTier does for a sensor link, and keeps what goatrope does that such an overlay does
not: a copy taken off a cable it is not part of, a receive-only listen mode, and a
default-deny relay that forwards only what the declaration names.

The mesh (in a goat deployment, NetBird) keeps the overlay's own jobs: addressing,
NAT traversal, peer keys, access between peers, and phones and desktops as endpoints.
goatrope adds what is missing on top of it, in six modules. Each module is one pull
request, tested in network namespaces on Ubuntu 24.04 and 26.04 before it merges.

| # | Module | What it adds |
|---|---|---|
| 1 | Relay service | `goatrope install` installs and `check` reads a relay unit; the relay is no longer WIP |
| 2 | TCP and link-initiated traffic | TCP rules; a `link-to-remote` direction for machines on the link that send first |
| 3 | Multicast | a rule may name a multicast group on the link, in either direction |
| 4 | Address proxy | a remote machine appears on the link under a local address of its own |
| 5 | Remote mirror | whole frames from a tap port, sent to a remote collector as ERSPAN over the mesh |
| 6 | Layer-2 lane | an opt-in bridge of one dedicated port to one mesh peer, filtered by declared EtherTypes and MAC addresses |

## 1. Relay service

- A declaration with `[relay]` makes `goatrope install` write `goatrope-relay.service`
  (`Restart=on-failure`; a refusal exits with the refusal code and is not restarted, so it
  stays visible). `check` reports the unit's state and the age of `relay.health`
  (stale after 10 s). `uninstall` removes the unit.
- A declaration may hold only `[relay]`; install then touches no tap port.
- `wip` is no longer required. `wip = true` is still accepted, and does nothing.
- `goatrope relay` keeps running the relay in the foreground, for a test.

## 2. TCP and link-initiated traffic

- `protocol = "tcp"`: the relay listens on the remote interface at `listen_port`. It accepts a
  connection only from the rule's `remote` address. It then opens a connection to the target
  from its link address and copies both ways until either side closes. Other connections are
  closed and counted as denied. `max_connections` (default 64) bounds each rule.
- `direction = "link-to-remote"`: the relay listens on its link address at `listen_port`. It
  sends what a machine on the link sends there to the rule's `remote` at `remote_port`, and
  sends replies back (UDP), or copies both ways (TCP). `sources` (required) lists the link
  addresses accepted. The link is not authenticated, so the list is the control.
- For TCP, `direction` is `remote-to-link` or `link-to-remote` (who opens the connection);
  `both` is refused, because a TCP connection always carries both directions.

## 3. Multicast

- `remote-to-link` with a multicast `target`: datagrams from the remote are sent to the group
  on the link interface, with the declared `ttl` (default 1).
- `link-to-remote` with a multicast `group`: the relay joins the group on the link interface
  only, and sends each datagram from a declared `sources` address to every listed `remote`
  (unicast through the tunnel, which carries no multicast). A second relay at the far end can
  send the stream onto its own link as a group again.
- Joining sends IGMP (IPv4) membership reports on the link. These are the only frames
  multicast adds.

## 4. Address proxy

- `[[relay.proxy]]` names a local `address` that stands for one `remote` peer. The relay adds
  that address to its link interface only after an ARP probe (RFC 5227) finds no other
  holder. It then announces it, and rules may use it as their link-side address
  (`link_address`).
- The address is held only while the remote's tunnel is up. On the mesh and the boundary
  transport, that means the WireGuard peer that owns the remote address has a handshake
  younger than 180 s. When it is not up, the relay removes the address, so machines on the
  link stop getting ARP replies for a dead path, and probes again before taking it back.
- It is still default deny: only the rules' ports on the proxy address are forwarded. The
  kernel does not route to the remote, and IP forwarding stays off.

## 5. Remote mirror

- `[[tap.mirror]]` on an inline or listen tap: frames arriving on the named tap ports go,
  through a tc `mirred` action, to an ERSPAN type II interface goatrope makes, keyed by the
  declared session and addressed to a collector over the mesh interface. The optional
  `filter` is a BPF filter compiled by tcpdump. The tap's own rule stands: nothing is sent
  onto the tapped link.
- The outer packets may be fragmented (`nopmtudisc`), so a full-size frame crosses a mesh
  whose MTU is below 1,500.
- A goatrope with `source = "erspan"` whose underlay is the mesh interface is a collector for
  it; so is any ERSPAN receiver.

## 6. Layer-2 lane (opt-in)

- `[[relay.l2]]`: one dedicated `port` (never a tap port and never the relay's link
  interface), bridged with a GRETAP interface to one mesh `peer`. It is refused unless the
  table has `accept_layer2 = true`, and the declared `ethertypes` and `macs` lists
  (required, no default).
- tc flower filters on both bridge members pass only the declared EtherTypes, and from
  across the tunnel only the declared source MAC addresses. Everything else is dropped and
  counted. STP is off, and no address is set on the bridge.
- The GRETAP interface is taken down when the peer's handshake is older than 180 s, and
  brought back up when it is fresh again. The outer packets may be fragmented, so the lane
  carries 1,500-byte frames.
- The risks ADR 0002 lists for a layer-2 tunnel remain in this lane, inside the declared
  lists. That is why it is a separate table that must be accepted by name, and never the
  relay's default.

## Validation

Every module adds one phase to `tests/netns/test_tap.py`, using namespaces and real
WireGuard between them. It must pass on Ubuntu 24.04 and 26.04 in CI before the module
merges. Module 6 also has to pass a run in the emulated arm64 VM (`tests/arm64/run.sh`).
Before a release, every phase runs once on two machines joined by a real NetBird mesh. The
CHANGELOG records each phase's result.

| Module | The phase shows |
|---|---|
| 1 | install writes the unit; check 0 with the relay active, 3 stopped or stale; a refusal is not restarted; uninstall leaves nothing |
| 2 | TCP both ways through a rule; a connection from another peer denied; `max_connections` enforced; a link-initiated UDP and TCP flow; a source not listed denied |
| 3 | a group stream from the link reaches two remotes; a remote's datagrams arrive on the link as the group; no other group joined |
| 4 | the address is refused while another machine holds it; held and answering ARP while the peer handshakes; removed within 180 s once it stops; forwarding stays off |
| 5 | every frame from the tap port arrives at a goatrope collector over WireGuard, 1,500-byte frames included; filtered frames do not; nothing sent on the tapped link |
| 6 | refused without `accept_layer2`; ARP and a declared EtherType cross; an undeclared EtherType or MAC dropped; lane down when the peer stops |

## Amends ADR 0002

ADR 0002 chose the fixed-port forwarder and left out the other two shapes. This ADR
adds the address-level proxy as module 4. It adds the layer-2 tunnel only as the
opt-in lane in module 6, and keeps the fixed-port forwarder as the default.
